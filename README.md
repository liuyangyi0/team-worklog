# Team Worklog · 工作完成记录

一个轻量的团队工作记录与项目协作工具，记录“原定谁负责、实际谁完成”，支持公开浏览、多人维护和不可删除的操作日志。

当前版本：**1.14.0**。前端采用 React、Vite、Tailwind CSS 和 lucide-react；后端使用 Node.js 24 自带的 HTTP 与 SQLite，无需单独部署数据库。

## 功能

- 多项目、项目配色、常用成员、原定负责人和实际完成人多选；结束的项目可归档收起。
- 跨项目总览：项目负责人、阶段、目标交付日、关键里程碑、逾期/阻塞任务，以及登录后可见的交接缺项和变更数量。
- 项目里程碑：计划/实际达成日期、手动状态、任务与受保护资料关联，独立于任务完成判定。
- 需求变更台账：原约定、调整内容、提出/确认事实、工期影响、关联任务/里程碑、执行状态与完整不可改历史。
- 任务说明、子任务、评论、跨项目人员总览、按人汇总及公开操作日志。
- 勾选多条记录批量标记完成、调整优先级/计划日期或批量删除，一次撤销。
- 计划完成日期、优先级、临期/逾期提示、个人待办与站内提醒。
- 跨项目任务依赖、循环依赖校验、自动/手动阻塞、配合人员和“需要我配合”。
- 搜索、筛选、排序、分页、截图模式、PNG 图片、Excel 可直接打开的 CSV 表格与 JSON 导出。
- 多人编辑版本冲突保护、删除撤销、SQLite 持久化与完整备份。
- 项目资料目录、批量/整目录分片续传、不可变版本、冲突候选、正式版与固定交付归档。
- 交接资料清单：按项目类型生成起步清单、分阶段、必需项与完整度、按项上传自动归档、自定义模板库。
- 随手记：现场设置、口头约定、文件收发按时间线留档，可补记发生日期、附件、关联资料项和任务。
- 同一事项可连续补充，独立保留记录人、发生日、登记时间和附件；原事项删除不级联删除补充。
- 新记录附件固定引用具体文件版本，旧关联明确“未固定版本”；人工更正引用有冲突保护。
- 项目大事记与统一查档：登录后跨项目查询记录、里程碑、变更、文件历史版本和交付归档，直接定位原始内容。
- 软件/设备/数据库资源、多地址和环境、跨项目资源及账号复用、加密密码历史与成员披露日志。
- 加密文本配置、正式发布、各资源/环境实际使用与回退记录。
- 自定义软件/硬件分类、六种字段类型、先选分类的动态表单、字段停用与历史保留。
- 多现场项目部署去向、客户/位置/入口/版本/维护人、资源关联和部署回收站。

完成规则：实际完成人或完成日期任填一项即完成；两项都空为未完成。计划日期、阻塞标记和配合人员不会改变完成状态。统计只计叶子任务，避免父子重复计数；共同完成在每位实际完成人名下各计一项。

## 快速运行

需要 Node.js **24.19 或更新的 24.x**。

```sh
git clone https://github.com/liuyangyi0/team-worklog.git
cd team-worklog
npm ci
npm test
npm run build
npm start
```

打开 [http://127.0.0.1:8766/worklog/](http://127.0.0.1:8766/worklog/)。工作记录公开可浏览；项目资料、资源、账号、配置登录后访问，所有注册成员可维护。

公开版使用虚构的示例项目和注册名单。先通过服务器私有环境设置 `ADMIN_PASSWORD` 创建管理员，管理员登录后在账号菜单的“成员与邀请”为指定姓名生成个人邀请码；成员凭姓名和邀请码注册。正式使用时请先修改 [registration.mjs](registration.mjs) 中的名单；未命中名单会提示“请填写真实姓名”。已存在账号继续可用，不自动合并历史同名账号；真实名单和运行数据不在此仓库中。

开发前端运行 `npm run dev`。后端也需要运行，并把 `APP_ORIGIN` 设置为实际前端地址，例如 `http://127.0.0.1:5173`。

## 配置

通过进程环境变量配置，程序不会自动加载 .env 文件。

| 变量                        | 默认值                | 用途                                                          |
| --------------------------- | --------------------- | ------------------------------------------------------------- |
| HOST                        | 127.0.0.1             | 后端监听地址                                                  |
| PORT                        | 8766                  | 后端端口                                                      |
| DATA_DIR                    | data                  | 数据库及备份的数据目录                                        |
| APP_ORIGIN                  | http://127.0.0.1:8766 | 浏览器访问来源，包含协议和端口                                |
| ADMIN_LOGIN                 | admin                 | 初始化管理员账号名；旧库已占用 admin 时另选，不会给旧账号提权 |
| ADMIN_PASSWORD              | 未设置                | 首次创建管理员账号并领取邀请；私有环境设置，至少 8 位         |
| FILES_DIR                   | DATA_DIR/files        | 私有原件和上传分片目录，不能放进公开静态目录                  |
| WORKLOG_MAX_FILE_BYTES      | 268435456             | 单件默认256MiB                                                |
| WORKLOG_STORAGE_QUOTA_BYTES | 21474836480           | 文件存储及活跃上传预留总配额，默认20GiB                       |
| VAULT_MASTER_KEY            | 自动生成独立文件      | 32字节hex/base64密钥；未设置则使用DATA_DIR/.keys/vault-v1.key |
| WORKLOG_MIN_FREE_BYTES      | 268435456             | 写入分片/原件前及备份前保留的可用空间，默认256MiB，允许0      |
| BACKUP_DIR                  | DATA_DIR/backups      | 完整备份目标，可指向独立卷/挂载存储                           |
| BACKUP_KEEP                 | 30                    | 完整备份保留份数，密钥单独备份                                |

管理员不是内容编辑的唯一入口；所有注册成员都能维护全部项目和记录。账号密码由本人修改；任务、评论、项目等内容变更保留公开日志，原始日志不可通过页面或接口改删。误贴敏感内容时，管理员可追加遮蔽记录，公共接口隐藏该条原文并保留处理人和时间；须先修改当前正文、检查其他副本并更换已泄露的真实密码。

## 部署与备份

1. 在部署目录运行 `npm ci` 和 `npm run build`。
2. 配置实际的 `APP_ORIGIN` 与独立的 `DATA_DIR`，修改注册名单。
3. 使用 `npm start`，或按 [worklog.service](worklog.service) 中的 systemd 示例部署。
4. 如使用 Nginx，可参考 [nginx-location.conf](nginx-location.conf)，应用路径为 `/worklog/`。
5. 数据保存在 `DATA_DIR/worklog.sqlite`，备份使用 `npm run backup`，包含数据库、全部历史原件和摘要清单；密钥需单独备份；systemd 定时备份示例默认在北京时间每天 03:15 执行。

服务文件中的 `/srv/worklog`、`/usr/bin/node` 是示例路径；实际访问来源通过服务器私有的 `admin.env` 设置 `APP_ORIGIN`，不要把真实域名、账号或密码写回公开源码。

`deploy.sh` 只安装本项目的 systemd 服务与备份定时器，不会自动改写 Nginx 配置。更新应用时保留数据目录；服务启动会兼容迁移现有数据库。

## 测试

```sh
npm test
npm run build
```

另有二十三组浏览器回归，覆盖记录编辑、子任务/评论、待办/提醒、任务依赖、批量操作/归档/表格导出、交接清单/随手记，以及文件上传/交接/账号/配置与手机布局，均使用临时数据库，不连接生产服务。准备 Playwright 和 Chromium 后运行：

```sh
npm install --no-save --package-lock=false playwright
npx playwright install chromium
npm run test:browser
```

可通过 `PLAYWRIGHT_MODULE_PATH`、`PLAYWRIGHT_EXECUTABLE_PATH` 指定已有的工具与浏览器。

## 1.12.0 项目推进与变更

侧栏“跨项目总览”集中查看项目管理资料，可按负责人、阶段、关键词和归档情况筛选，直接进入关键任务、里程碑、资料或变更台账。项目负责人/阶段/目标交付日为公开资料；任务数量仍按原有 OR 完成规则与叶子任务统计，不用工作条数冒充项目进度。

项目模块“项目里程碑”保存关键节点，可关联本项目任务、文档身份或固定文件版本。状态为计划中、进行中、已达成、已取消，实际日期可空，达成由成员手动登记；任务完成不自动达成里程碑，里程碑达成也不改写任务。公开响应仅包含公开里程碑与任务信息，文件关联仅登录可见。

“需求变更”需登录，所有注册成员可维护。确认状态和执行状态独立保存，不增加审批角色；登记工期影响不会自动修改计划日期。退回待确认会清当前确认人/日期，旧确认事实保留在历史。新增修改、移除恢复均保留完整不可改快照，长文本和关联对象当时名称不随之后修改丢失。

## 1.13.0 项目过程记录与查档

随手记新关联的附件自动固定为当次具体文件版本，后续上传不会改变引用。主入口查看当时原件，另可查看最新版；历史关联保留原状并明确“未固定版本”，不能推测当时依据。成员可选择有效历史版人工固定或更正，版本冲突会提示重新核对，修改保留前后记录。

每条随手记都可“补充一条”，同一事项的补充独立保存正文、作者、发生日期及附件；事项详情连贯展示。编辑纠错继续保留，原事项软删除不删除已有补充，恢复与历史留存规则不变。

项目内“项目大事记”聚合业务记录、里程碑登记/达成、变更登记/确认、正式文件发布和固定交付归档；不把每次下载或改名都当成业务事件。发生日期与系统登记时间分开显示，旧事件没有发生日快照时不反推。

侧栏“统一查档”可切换本项目/全部项目、来源、日期和关键词，检索资料元数据、来源路径、历史文件名及记录正文。文件结果对应具体版本，跳转不会替换工作版；本轮不解析文件正文或执行OCR。两种档案视图均需登录，账号密码、配置正文、文件原件不会进入查询响应。现有任务完成规则、父子独立、叶子统计和成员内容权限均保持不变。

## 1.14.0 文件收发记录

在现有随手记中选择“文件收发”，即可区分收到与发出，填写往来方、发生日期、具体时间（北京时间）与渠道；附件继续对应固定文件版本，后续上传不会替换当时的收发依据。同一事项的每次补充独立填写收发事实，不继承上一条的方向、往来方或时间。

列表、项目大事记和统一查档支持收到、发出、未区分收发筛选，关键词可查往来方与渠道，并与现有分类、标签、待整理和交接清单配合使用。旧“文件转存”沿用原记录与附件，不自动猜测方向或日期；未填写的发生日期和具体时间不会用登记时间代替。具体时间仅在填写日期时可填，其他收发字段可空，支持先记后补。这里记录已经发生的收发事实，不实际发送文件或邮件。所有注册成员均可维护，登录要求、版本冲突保护、只读历史与任务完成规则保持不变。
